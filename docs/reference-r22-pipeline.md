# R22 动作管线审查

2026-09-20。范围为本机已知制作/运行文件的只读审查；没有原版逐招录像测量。以下是可由代码确认的问题及制作建议，不能作为还原视觉验收。未创建索引；仓库没有 `.codegraph/`，当前没有可调用的 codebase-memory 索引工具，按 AGENTS 对已知文件直接读取。

## 坐标和骨骼

- 参考 Blender 人体正面是 **+Y**，上方是 +Z，角色右侧是 +X。旧 `set_pose` 的手/脚参数以 **-Y 为前**，通过 `front(v)=(x,-y,z)` 转一次；局部骨骼旋转另用 rest-space 反射矩阵共轭。新控制器应全部使用 Blender 的 +Y 正面，不要混用旧参数和运行时坐标。
- 导出 Root 的静止基矩阵把其局部 +Y 映射到 Blender +Z，因此 `Root.location.y=height` 是上下移动，绕 Root 局部 Y 是人体转向。运行时 COORD 以负 Z 为前。不要看到三个不同的轴就再补一次翻转。
- `Arm_R/L` 是上臂的肩关节，`Hand_R/L` 实际是前臂的肘关节，`Tool_R/L` 才在手腕末端。`Elbow_R/L` 是上臂下的旁支蒙皮辅助骨，旋转它不会改变真正前臂位置。`Leg_R/L` 是小腿，`Knee_R/L` 是辅助骨；目前没有独立脚掌骨。
- 当前武器渲染按 Arm、Hand 的完整姿态矩阵绑定，没有额外左右镜像矩阵。R21 的 Hand_R roll 是前臂轴向旋转，不是独立手腕转动；它会把整个巨大刀刃绕肘轴调整。不能靠衰减 Elbow 辅助骨来解决刀臂运动学问题。

## 已确认的问题

1. `build_claw_blender.py:192` 的 `set_pose` 每一帧重置所有骨骼，只有 twist、lean、height、双腕位置、双踝位置和 root_pitch。twist 固定同步分摊 Root 22%、Torso 50%、Chest 28%；没有髋先行、胸滞后、肩前伸、肘轨迹和手刃朝向的独立控制。两腿先放到相同弯曲起始角，再让 IK 求解。
2. 文件第 175 行创建了双肘 pole 控制器，但腕 IK 没设置 `pole_target` / `pole_angle`；这些肘控制器目前并不影响胳膊弯曲方向。腿部 IK 则确实绑定了 knee pole。只给腕部几个点无法保证每次都以希望的肘姿通过。
3. 足部控制器只有位置，无脚底方向和脚跟/脚尖接触控制。支撑阶段固定一个端点不等于整片鞋底贴地。当前 rig 无脚掌骨，最低成本应固定小腿末端接地点并限制小腿倾斜，若要脚尖蹬地需要补渲染兼容的脚部关节或独立鞋部控制。
4. R20 在 `author_weapon_combat_r19.py:121` 烘焙 IK **以后** 才给导出 Root 加整身转角。原来固定的脚部坐标因此跟着旋转，.blend 也不包含这段运行时转角。必须在 IK 求解前将转角放在场景中，并重算世界固定的支撑点。
5. R21 `AdaptedWeaponAnimation` 用来源骨骼轨迹，但用自定义 smoothstep COORD 替换来源根位移。`correctRootJoint` 正确清除了来源水平 Root 位移，却没有同步重算来源足部轨迹。因此存在支撑脚相对地面滑动的数学风险；单调前进距离测试不检查这个问题。
6. `PrototypeComboActionAnimation` 在 WALK/RUN 时把腿换回实时步态，保留攻击的 Root/上身。它适合容许自由行走的轻攻击，不适合要求特定踏步、支撑和重心转换的强承诺全身动作。此类动作应使用完整腿部轨迹并明确移动输入是否暂时受限。
7. 原 `WeaponCombatSystem` 只在接触结束后接受队列，且必须等整段 duration 后执行 `cancel -> idle -> request`。每击退回待机再出下一击，不能保存上一击的余势和支撑。链状态还只有 tick/second，没有武器形态，换形态可沿用另一形态的二段标记。
8. 旧几何验收只检查头部距离。它既不检查身体/另一臂/地面穿插，也不验证刃面法向、接触时刻、脚滑或连招边界连续性。自动 bank 若只写 JSON 同样会造成制作场景和最终文件不一致。

## 最小可复现制作管线

1. 保留 Epic Fight 20 骨骼格式和自有武器网格；新增一个独立 R22 制作脚本，旧动作可作回退。控制器约定统一为 Blender +Y 向前。
2. 每个已实际观察的原版招式先登记来源及时间点，然后逐段标注左/右脚接触、支撑切换、髋/胸旋转、肘和刃端轨迹。不用未观看的视频标题推算动作。
3. 给 pelvis、Torso、Chest、Shoulder_L/R 独立曲线；双腕位置、双肘 pole、前臂轴向 roll 分开。全身朝向和世界位置在同一场景中求解，禁止导出后再补 Root yaw。支撑脚目标在其接触区间用世界坐标保持不动，摆动脚按观察轨迹移动。
4. 在 Blender 完整制作前进动作；从同一场景导出 **水平根位移 COORD** 与去掉该平移后的关节动画。控制器、根位移和 IK 用同一采样时钟烘焙，不能用另外一条通用 smoothstep 代替已制作的根轨迹。遭遇墙体使位移受阻属于另一个运行时足部适配问题，正常平地必须先对齐。
5. 用同一长时间线制作一套连击，再按可接招点拆片。下一段第一帧使用上一段的退出姿态及速度；无输入时才走完整回待机收势。运行时在接触全部完成后接下一片，直接从当前姿态 link，不中插 idle。保留原伤害窗口及每击独立去重。
6. 验收至少记录：支撑区间足端世界漂移；骨骼位置/速度在片段交界的差值；真正刀刃端相对目标的通过时间；头/胸/非攻击臂/地面间隙。双端刀要检查两个端点，不能只量一个腕关节。
7. 用最终导出的文件重新加载到 Blender 或运行时预览，正、侧两机位与实际观看过的参考逐段对照。验收画面使用最终产物，不能只展示未包含导出修正的 .blend。

这套方案保留现有导出器、Epic Fight 播放与服务器伤害逻辑。最关键的改动是“独立身体控制 + 求解前全身转向 + 同源根轨迹/足点 + 不经过 idle 的连击出口”，而不是再次给统一手臂摆动曲线增加幅度。

## R22 连招播放包复查

按当前 Epic Fight 21.17.3.1 的本地源码复查：`ServerPlayerPatch.sendToAllPlayersTrackingMe` 使用包含玩家自身的同步发送，所以 `WeaponCombatSystem.start` 会给本人发送 Epic Fight 动画播放包及自定义 `WeaponAnimationPayload` 两种通知。

正常到达顺序下没有发现确定的重复播放：自定义接收器先查 `ClientAnimator.isPlaying`，该方法检查 `getRealAnimation`；`LinkAnimation.getRealAnimation` 返回下一段目标动画，因此处于 link 过渡时也能正确跳过自定义重复通知。新连招分支直接调用 `start`，不经过 `finish`、`cancel`、空视觉状态或 `BIPED_IDLE`；正常结束和明确取消仍恢复待机。

存在一项未复现的设计隐患：自定义包只包含 move ID，没有会话编号或开始 tick。如果过期通知在接收时已不再是当前动作，单凭 `isPlaying` 无法识别旧请求。后续可在确认 Epic Fight 同步可靠后去掉冗余自定义播放通知，或为回退通知加会话校验。此次审查只报告，没有改动这些生产路径，也不把这一风险说成已观察到的双播故障。

连招 GameTest 验证的是服务器状态和伤害，不证明客户端 packet/link 连续性。新利爪 QA 记录真实动作请求，但该轮没有记录客户端 animator 时间是否重置，而且有漏帧；后续需要额外记录实际动画身份、link 目标和时间，才能排除瞬间重播。
